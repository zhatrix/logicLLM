# logicLLM 全过程复现指南

> 目标：在一台 Apple Silicon Mac 上，从空目录搭出一个**可运行的物流行业大模型**——
> MLX LoRA 微调 Qwen2.5-7B + 知识库 RAG + 业务工具调用 + Web/API 服务。
> 本文按实际执行顺序记录每一步的命令、耗时、决策和踩坑，按顺序照做即可复现（约半天，其中训练约 1 小时）。

---

## 0. 环境与前提

| 项 | 本次实际值 | 说明 |
|---|---|---|
| 机器 | M4 Max / 128GB 统一内存 | 7B 4bit 训练峰值内存约 74GB（不开 grad-checkpoint）；64GB 机器请在 `scripts/train.sh` 加回 `--grad-checkpoint`（峰值 ~14GB，慢 30%） |
| Python | uv 管理的 3.12 venv | 不要用系统 miniconda（torch 有 OpenMP 冲突） |
| 推理回退 | Ollama + `qwen2.5:3b` | 零配置先跑通应用层，不依赖训练 |
| 网络 | 能访问 huggingface.co | 不能的话 `export HF_ENDPOINT=https://hf-mirror.com` |
| 云 API | 无 | 全程本地，无任何 key |

需要下载的模型（自动）：`mlx-community/Qwen2.5-7B-Instruct-4bit`（4.3GB）、`BAAI/bge-m3`（2.2GB）。

```bash
# 预先后台拉取，省等待
uv run hf download mlx-community/Qwen2.5-7B-Instruct-4bit &
uv run hf download BAAI/bge-m3 &
```

> 坑：`hf download` 进程若被父 shell 超时杀掉会留下 `.incomplete` 分片，重新执行同一条命令即可续传。

## 1. 先定路线（5 分钟）

四种形态里选了 **微调 + 应用一体**，场景四选四（客服问答 / 单据抽取 / 路径调度 / 行业知识）。

## 2. 工程骨架（约 1 小时）

```bash
mkdir logicLLM && cd logicLLM
uv init --name logicllm --python 3.12
uv add mlx-lm fastapi "uvicorn[standard]" httpx pydantic numpy sentence-transformers huggingface-hub openai pyyaml
# pyproject.toml 加 hatchling build-system 并声明 packages = ["logicllm"]，否则 scripts/ 里 import 不到包
uv sync
```

目录与职责（详见 README）：

```
logicllm/config.py          环境变量配置（LLM_BACKEND=mlx|ollama、LLM_ADAPTER…）
logicllm/llm/client.py      OpenAI 兼容客户端；tool_calls 解析 + 文本 <tool_call> 兜底 + 断连重试
logicllm/rag/kb.py          Markdown 按标题切块 → bge-m3(mps) → numpy 余弦检索
logicllm/tools/*.py         @tool 装饰器自动注册：运单 SQLite、计费、时效、Dijkstra 路径、TSP 排序、地址解析
logicllm/agent/prompts.py   系统提示词 + RAG 注入块
logicllm/agent/core.py      工具循环（非流式 / SSE）
logicllm/server/app.py      FastAPI：/ 、/api/chat、/api/chat/stream、/v1/chat/completions、/api/health
data/kb/*.md                8 篇物流知识（自己写的，约 6k 字）
scripts/                    build_kb / gen_sft / train.sh / serve_mlx.sh / eval.py / fuse.sh
eval/cases.jsonl            20 条规则评测用例
```

### 2.1 关键设计决定

1. **工具调用协议统一用 OpenAI 原生 `tools` / `tool_calls` / `role=tool`**，不要自己发明文本协议。
   原因：mlx_lm server 和 Ollama 都会套 Qwen 的 chat template，把 tools 渲染进 system、把 `<tool_call>` 解析成 `tool_calls`；
   mlx_lm 的训练集也支持 `"tools"` 字段——训练与两个推理后端格式天然一致。
   线上请求里 `function.arguments` 传 **JSON 字符串**；训练 jsonl 里传 **dict**。
2. **mlx server 请求的 `model` 必须是 `"default_model"`**，否则它会去 HF 拉你写的名字。
3. 端口：本机 8000 被别的项目占用，应用用 **8010**（`make serve PORT=xxxx` 可改），mlx 用 8080。

### 2.2 先用 Ollama 跑通应用层

```bash
ollama pull qwen2.5:3b
uv run python scripts/build_kb.py          # 35 个切块，检索抽查正常
LLM_BACKEND=ollama uv run uvicorn logicllm.server.app:app --port 8010
curl -X POST localhost:8010/api/chat -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"帮我查一下运单 LL2026080258"}]}'
```

此时四条链路（运单查询、运费、调度、追问运单号）和流式都通了。3B 基座的短板也暴露出来：算运费会漏掉箱体尺寸——这就是微调要修的。

> 运单库由 `init_db(seed=42)` 确定性生成，真实运单号如 `LL2026080258`；不要在评测/示例里编号。

## 3. 基线评测（微调前）

```bash
bash scripts/serve_mlx.sh                   # 此时无 adapter，纯 7B 基座，:8080
LLM_BACKEND=mlx uv run python scripts/eval.py
```

基座 7B + RAG + 工具：**0.825**（客服 0.83 / 知识 0.94 / 抽取 **0.00** / 调度 1.00）。
抽取 0 分是因为基座调 `parse_address` 后用散文作答，不按要求输出 JSON。

> 注意：长 prompt（~2.4k token）下 mlx server 串行处理，20 条用例跑了 80 分钟。Python 输出重定向到文件会被缓冲，后台任务一律 `python -u` / `PYTHONUNBUFFERED=1`，管道里的 grep 加 `--line-buffered`。

## 4. 合成训练数据

```bash
bash scripts/serve_mlx.sh &                 # 7B 基座当教师
LLM_BACKEND=mlx uv run python -u scripts/gen_sft.py --n-kb 240 --n-tool 400 --n-extract 240 --n-route 120
```

`scripts/gen_sft.py` 的四路数据：

| 类型 | 来源 | 数量 |
|---|---|---|
| 客服 + 工具调用 | 模板问法 + **真实执行工具**得到结果，再模板化答案（轨迹 100% 正确） | 400 |
| 单据抽取 | 程序合成地址 → 规则解析器打标签；70% 直接输出 JSON，30% 先调 `parse_address` 再输出 JSON | 240 |
| 路径/调度 | 模板 + 真实工具结果 | 120 |
| 行业知识问答 | 知识库切块 → 教师模型生成 3 个 Q/A（约 2 小时，结果缓存在 `data/seed/teacher_kb_qa.json`，之后自动复用） | 244 |
| 手写种子 | `data/seed/handwritten.jsonl` | 10 |

**最终版本的三条硬规则**（每条都是踩坑后加的，见第 6 节）：

1. **所有样本都带 `tools`**（线上永远带）。
2. **所有样本的 system 都注入与线上相同的检索上下文**（`_context_for()` 复用 `KnowledgeBase.search`）。
3. **每条含工具调用的轨迹额外拆出"到该次 tool_call 为止"的前缀样本**（`--mask-prompt` 只训最后一条 assistant）。

最终数据量：train 1435 / valid 124，token 长度 p50 2757、max 3781。

## 5. 训练 → 上线 → 评测

```bash
bash scripts/train.sh 200        # mlx_lm lora：batch 2，16 层，lr 1e-5，max-seq 4096，--mask-prompt
bash scripts/serve_mlx.sh        # 基座 + --adapter-path（应用侧再在请求里带 adapters 绝对路径）
LLM_BACKEND=mlx uv run python scripts/eval.py
LLM_BACKEND=mlx uv run uvicorn logicllm.server.app:app --port 8010
```

训练过程（M4 Max，约 29 分钟 / 100 步）：

| Iter | Val loss |
|---|---|
| 1 | 1.280 |
| 100 | 0.129 |
| 200 | **0.104** |

（前几轮实验：600 步会过拟合，Val loss 300–400 步最低，所以定 200–300 步。）

评测：**0.825 → 0.880**，抽取 0 → 0.8，运费计算不再漏尺寸，全量评测 216s（基线 4934s）。

把长任务串成后台流水线最省心（训练 → 起服务 → 评测），用 `nohup … < /dev/null & disown` 脱离父 shell，否则命令超时会把训练一起杀掉：

```bash
cat > /tmp/pipeline.sh <<'EOF2'
cd ~/Project/MyLLM/logicLLM; export PYTHONUNBUFFERED=1
bash scripts/train.sh 200 2>&1 | grep --line-buffered -E "Val loss|训练完成|Traceback"
nohup bash scripts/serve_mlx.sh > /tmp/mlx.log 2>&1 < /dev/null &
until curl -s localhost:8080/v1/models >/dev/null; do sleep 2; done
LLM_BACKEND=mlx uv run python -u scripts/eval.py 2>&1 | grep --line-buffered -E "^(✅|🟡|❌|总分|  [^ ])"
EOF2
nohup bash /tmp/pipeline.sh > /tmp/pipeline.log 2>&1 < /dev/null & disown
```

## 6. 踩坑全记录（按时间顺序，这部分最值钱）

前三轮微调看起来"没效果甚至更差"，其实是下面几个问题叠加。每条都给出**如何发现**和**解法**。

### 6.1 Ollama 会吞掉自定义的 `<tool_call>` 文本协议
- 现象：content 为空或只剩裸 JSON。
- 原因：Ollama 的 Qwen 模板自己解析 `<tool_call>` 成 `tool_calls`。
- 解法：全面改用 OpenAI 原生 tools 协议（第 2.1 节）。

### 6.2 mlx_lm server 对 `default_model` 不应用 `--adapter-path`
- 现象：微调后行为与基座**完全一致**；离线 `mlx_lm.load(adapter_path=…)` 却正常。
- 原因：`server.py` 的 `load()` 先把 `default_model` 换成真实路径，再用真实路径查 `_adapter_map`，永远查不到。
- 解法：应用侧每个请求带 `"adapters": "<绝对路径>"`（`config.LLM_ADAPTER` 自动设置）。
- **诊断方法**：训练完先离线跑 `mlx_lm.load(base, adapter_path=…)` 对训练集原样本复现；再对比 server 输出。两者不一致 → server 没挂上。

### 6.3 `mlx_lm fuse` 合并进 4bit 基座后 LoRA 失效
- 现象：合并模型在训练集原样本上也输出基座行为。
- 解法：不合并，直接挂 adapter；确需合并用 `--de-quantize`（`scripts/fuse.sh`，输出 fp16 约 15GB）。

### 6.4 `--mask-prompt` 只训最后一条 assistant 消息 → 学不会发工具调用
- 现象：抽取（最后一条是 JSON）学得很好；但**所有工具题都不调工具**，还编"请稍等我来查询"。关 RAG 也一样。
- 原因：多轮轨迹 `[user, assistant(tool_call), tool, assistant(answer)]` 中，tool_call 那条被当作 prompt 掩掉。
- 解法：`gen_sft.py` 把每条轨迹额外拆出前缀样本 `[…, assistant(tool_call)]`。

### 6.5 训练/推理 prompt 分布不一致
- 现象：离线对训练样本能复现，对线上 prompt 不行。
- 原因：线上 system 里注入了检索上下文、请求里带 tools，而训练样本没有。
- 解法：第 4 节的规则 1、2。

### 6.6 样本超过 `max-seq-length` 被截断 → Val loss NaN
- 现象：100 步时 `Val loss nan`。
- 原因：231 条样本 > 3072 token，截断后目标 token 为 0，0/0。
- 解法：`--max-seq-length 4096`；训练前用 tokenizer 统计长度分布：
  ```python
  tok(tok.apply_chat_template(r["messages"], tools=r["tools"], tokenize=False)).input_ids
  ```
  （注意 `apply_chat_template(tokenize=True)` 返回 BatchEncoding，`len()` 是 2，不是长度。）

### 6.7 流程类
- `pkill -f pipeline.sh` 杀不掉已 `disown` 的流水线子进程，要连 `mlx_lm lora` / `gen_sft.py` 一起杀，否则两条流水线互相覆盖权重。
- 评测关键词别太死："3 倍" vs "3倍"（eval.py 已做去空格比较）；省份全称"新疆维吾尔自治区"是合理输出。
- 知识库里写了"查询运单前需核对手机尾号"，模型就真的会先要尾号——知识库措辞会直接变成行为，按业务预期来写。

## 7. 最终状态与下一步

- 服务：`bash scripts/serve_mlx.sh`（:8080）+ `LLM_BACKEND=mlx make serve`（:8010，Web 界面）。
- 权重：`adapters/logistics-lora/adapters.safetensors`（200 步，Val 0.104，已 gitignore，需要单独归档）。
- 剩余失分：未指定服务类型时模型自行填 `经济`；7B 数值比较弱（"53 度 vs 70%"）。
  → 下一轮加"不带服务类型的运费问法"和"数值比较类知识问答"样本，再训 200 步（约 1 小时）。
- 接真实系统：替换 `logicllm/tools/waybill.py` 的 SQLite 为 TMS/OMS 接口；新增工具只需 `@tool(...)` 装饰。
